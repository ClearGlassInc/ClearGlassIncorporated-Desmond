## 1. Audit CI/CD workflows for permission bloat and secret exposure

**Status: done.** Audited all 48 pre-existing workflows.

### The good news first

The baseline is stronger than expected, and three things came back clean:

- **Every workflow declares top-level `permissions:`,** and 45 of 48 declare
  exactly `contents: read`. Job-level widenings are narrow and carry inline
  justifications. There is no `write-all` anywhere.
- **Every third-party action is pinned to a full 40-character commit SHA.**
  The only unpinned `uses:` values are local `./` paths. No drift.
- **No script-injection surface.** No workflow interpolates untrusted
  `github.event.*` fields (issue/PR titles, bodies, `head_ref`) into a `run:`
  block, and there is no `pull_request_target` trigger in the repo.

So this audit is not about permission bloat — that is already controlled. All
three findings are about **secret and data exposure**.

### Finding 1 (HIGH) — live revenue data published to a publicly-readable step summary

`sales-ops-briefing.yml` ended its run with:

```
python -m app.sales_ops_briefing --email | tee "$GITHUB_STEP_SUMMARY"
```

`render_markdown()` in `app/sales_ops_briefing.py` emits yesterday's revenue,
month-to-date revenue and order counts, month-end forecast, and per-order
amounts and IDs for new, stalled and at-risk deals. `tee` wrote all of it to the
Actions step summary.

**Why this is high, not medium:** this repository is a public GitHub Pages site
— it carries a `CNAME` for `www.clearglassinc.com`. Actions step summaries and
run logs are readable by anyone who can read the repository. The scheduled run
at 11:17 UTC daily was therefore publishing commercial performance data to a
persisted, publicly-readable artifact, indefinitely.

There is a second, subtler exposure in the same step. `_make_session()` rewrites
the DSN scheme (`postgres://` → `postgresql://` → `postgresql+psycopg://`)
before handing it to `create_engine`. Actions secret masking is a literal-string
match against the registered secret value, so **the rewritten DSN no longer
matches `DATABASE_URL` and is not masked.** Any diagnostic that echoes the
rewritten URL — a SQLAlchemy connection error, for instance — bypasses redaction.

**Fixed.** The briefing body now goes to email only, which is its intended
private channel. The step summary receives a fixed status line. Failure
diagnostics are captured to a file and deliberately not echoed, with the
masking-bypass reason recorded in a comment so the next editor does not
"helpfully" restore the output.

### Finding 2 (MEDIUM) — the broadest credential in the repo was job-scoped

`multi-repo-audit.yml` bound `CG_ORG_PAT` — a long-lived, org-scoped PAT with
`repo:read` + `read:org`, the highest-value credential here — at **job** level.
A job-level `env:` is visible to every step in the job, which in this job
included `pip install --quiet pip-audit` and `apt-get install jq`. Both execute
third-party code with the org PAT sitting in the environment.

**Fixed.** The PAT is now bound only to the two steps that call the GitHub API
(`Verify gh auth`, `Run audit pipeline`). The optional-secret skip behaviour is
preserved. A comment at the former location explains why it is deliberately not
set there.

**Still open:** the credential itself. A long-lived org PAT is the wrong shape
for this — a GitHub App installation token would be short-lived and
per-repository scoped. Tracked below.

### Finding 3 (MEDIUM) — `persist-credentials` defaults left tokens in the work tree

`actions/checkout` defaults to `persist-credentials: true`, writing the job's
token into `.git/config` where any later step can read it. Across the repo,
**67 checkout steps declare `persist-credentials` only twice.**

The exposure is real but uneven: it matters most in jobs that hold
`contents: write` *and* install dependencies after checkout, where a compromised
package could read a write-capable token. It is harmless in jobs that need the
persisted credential to push.

**Partially fixed.** Applied to the three checkouts touched by this change
(`sales-ops-briefing`, `multi-repo-audit`, the new `codeql-trial`). **Not**
blanket-applied to the remaining 64 — a sweeping change would silently break
every workflow that pushes via the persisted credential, and that is a change
that deserves its own reviewed PR rather than a drive-by edit inside an audit.
Tracked below.

## 2. Benchmark one AI workload on alternative accelerators (AMD)

**Status: blocked — the premise does not hold. No benchmark was run.**

I went looking for the workload to benchmark and there isn't one. Searched the
tree for `torch`, `transformers`, `onnxruntime`, `llama_cpp` and
`sentence_transformers`: **zero matches outside comments.** Specifically:

- Every LLM call in the repo is to a **hosted API** — Anthropic via `agent.yml`,
  OpenAI via `codex-autofix.yml`. No inference runs on our infrastructure.
- The only embedding code, `sentinel/sentinel/vectorstore.py`, is a deterministic
  **hashing stand-in** (`_DIM = 64`, bag-of-tokens, L2-normed) explicitly
  documented as a placeholder to keep the reference store dependency-free. It is
  not a model and would not benefit from an accelerator.
- `sentinel/requirements.txt` is FastAPI plus test tooling. No ML stack.
- Production is Render PaaS. We have no GPU capacity, owned or rented.

Benchmarking AMD this week would mean inventing a synthetic workload, measuring
it, and presenting the number as a procurement input — which would be worse than
not doing it, because it would look like evidence. **The honest output is the
trigger and the harness, ready to run when there is something real to measure.**

### Promotion trigger

Revisit when **either** condition holds:

1. A workload moves in-house — most plausibly embeddings, if
   `vectorstore.py`'s hashing placeholder is replaced by a real embedding model
   for SENTINEL retrieval. That is the one place in this codebase where a local
   model is a natural fit.
2. The Q3 spend model (item 6) shows hosted-API token spend on a trajectory
   where reserved or owned capacity wins on cost.

### Harness spec (to run when triggered)

Fix these before touching hardware, so the comparison is decision-grade:

- **Same workload, same data, both vendors.** Replay a captured production
  request trace, not a synthetic loop. A benchmark that does not resemble our
  traffic answers a question we did not ask.
- **Report p50/p95/p99 latency and throughput at a fixed accuracy bar** — not
  peak throughput. Peak numbers hide tail behaviour, and tail behaviour is what
  users experience.
- **Cost per 1M tokens (or per 1k requests) fully loaded**: instance hours plus
  the engineering time to keep the runtime patched. ROCm-versus-CUDA porting
  effort belongs in the cost column, not in a footnote.
- **Record the failure modes**, especially kernel/runtime gaps hit during
  porting. For a second-source decision, "what broke and how long it took to
  fix" is the finding.
- **Decision bar, set in advance:** AMD must win on fully-loaded cost by a
  margin wide enough to survive the migration effort, at equal or better p99. A
  narrow win is a loss.

Related radar entry: **DRA for accelerators** (`docs/TECH_RADAR.md`) — the
scheduling piece that a mixed NVIDIA/AMD fleet would need.

## 3. Review agent/tool permissions and sandboxing

**Status: done.** The finding is a two-tier split: enforcement is genuinely
strong in three subsystems, and entirely absent for the agent fleet.

### Tier 1 — real, tested enforcement

Three subsystems enforce permissions in code, and all three fail closed:

- **`clearglass-commerce/control-plane/app/governance.py`** — `score_action()`
  routes by risk tier; high/critical block on an approved `approvals` row.
  Verified the important property: an **unknown action defaults to high risk**
  ("defaulting to high risk (fail closed)"), and a low-confidence signal
  hard-gates on its own rather than relying on a score bump that could leave a
  low-base action under the threshold. Ran `python -m app.daily_loop --json`:
  `governance_failures: []`.
- **`app/security.py`** — `require_admin` gates mutating admin routes;
  `verify_startup_posture()` refuses to boot when `APP_ENV=production` and no
  `ADMIN_API_KEY` is set. Rate limits on checkout, webhook and approvals.
- **`sentinel/sentinel/rbac.py` + `policy.py`** — every retrieved `doc_id` is
  re-authorized against the source-of-truth ACL *after* the vector filter, so a
  poisoned or stale embedding degrades to "missed results", never "leaked
  results". The policy evaluator denies on any missing or unverifiable term.

This is a sound design and the sandboxing story for the commerce and retrieval
paths is in good shape.

### Tier 2 — the agent fleet declares permissions that nothing enforces

`agents/` holds 30+ agent definitions. Twelve of them (`outreach`, `analytics`,
`compliance`, `advertising`, `conversion`, `local-seo`, `partnerships`,
`market-intelligence`, `revenue-operations`, `content-authority`,
`campaign-strategy`, `account-discovery`) share a clean permission schema:

```json
"mode": "dry_run_by_default",
"permissions": ["read_public_sources", "draft_recommendations", "write_audit_events"],
"approval_required_for_external_actions": true,
"forbidden": ["bypass access controls", "send without approval", "spend without approval", "fabricate claims"]
```

**Nothing reads these fields.** Grepping every consumer of `agent.json` returns
three sites: `bots/artemis_ip_guardian_bot.py` (existence check),
`.github/workflows/artemis-deploy.yml` (validation), and a test. No loader maps
`permissions` to a capability set; no runtime consults
`approval_required_for_external_actions` before an external call. They are
documentation that looks like configuration.

**The inversion is the real problem.** The twelve agents with the *narrowest*
declared scope are the only ones that declare scope at all. The agents with the
broadest authority — `clearglass_executive` (which defines `action_scopes`,
`approval_tiers`, `escalation_scopes`, `default_authority`),
`percival_execution_agent`, `clearglass_agent_os`, `engineering_execution`,
`workflow_repair` — carry **no `permissions` key**. Their safety model is prose
in `safety_model` and `guardrails`: "never request, expose, infer, or store
secrets", "never fabricate… completed actions". Good rules, but prose in a JSON
file is not a control. It cannot be tested, and it degrades silently.

### Recommendation

Do not build a new enforcement layer. Wire the declared scopes into the one that
already works: map `agent.json` `permissions` onto `governance.py` action names,
and treat an undeclared or unmatched capability the way `score_action()` already
treats an unknown action — **high risk, gated**. That inherits the fail-closed
property and the audit ledger for free, and it turns the twelve well-formed
declarations into live controls rather than rewriting them.

| Add `permissions` blocks to the five broad-authority agents | High | Architecture | 2026-08-14 |
| Schema-validate `agent.json` in CI so new agents cannot ship without a scope | Medium | Platform | 2026-08-21 |

## 6. Model Q3 cloud spend against AI growth signals

**Status: partial.** I can quantify the CI load precisely from source, because
that is in the repo. Billing figures are not, so the model is a structure with
one dimension populated and the rest flagged as required inputs. Projecting
spend from invented rates would produce a confident-looking number with no basis.

### What is measurable from source: scheduled CI load

Parsed every `schedule:` trigger across all 49 workflows:

- **24 scheduled workflows**, totalling **~1,468 runs/month**.
- **`control-surface-feeds.yml` alone is ~730 runs/month — almost exactly half
  of all scheduled runs.** It is hourly (`17 * * * *`), and each run commits
  refreshed feeds and dispatches `pages.yml`. This is the single dominant CI
  driver by run count, and the first place to look for savings.
- Next tier, all every-6-hours (~122 runs/month each): `defender-watch`,
  `health-monitor`, `master-orchestrator`.
- **`master-orchestrator.yml` is the worst-case *minutes* driver**: 4 jobs at a
  360-minute timeout, 4×/day. Worth checking actual durations against that
  ceiling — a 6-hour timeout on a scheduled orchestrator is either a real
  long-running job or a default nobody revisited.

Worst-case ceiling across all scheduled work is ~244,000 job-minutes/month, but
that multiplies by `timeout-minutes`, so it is an upper bound and almost
certainly far above actual. **Real durations are the missing input** — they are
in the Actions API, not the repo.

**Cost caveat that changes the conclusion:** for a public repository, GitHub
Actions minutes are free on standard runners. If this repo stays public, CI run
volume is an *reliability and rate-limit* concern, not a spend line. The Q3
model's real exposure is Render services plus hosted LLM API tokens.

### Required inputs before this model is decision-grade

| Input | Source | Needed for |
|-------|--------|-----------|
| Render service + Postgres monthly cost | Render billing | Baseline |
| Anthropic + OpenAI token spend, 3-month trend | Provider billing | The AI growth signal itself |
| Actual workflow durations vs timeouts | Actions API | Replace the worst-case ceiling |
| Private-repo Actions minutes, if any | GitHub billing | Whether CI is a cost line at all |
| Storefront/admin hosting + bandwidth | Render/Vercel | Baseline |

### Growth signal to model against

Token spend is the variable that scales with AI adoption; everything else here
is roughly fixed. Model three trajectories (flat, 2×/quarter, 5×/quarter) and
find the crossover where reserved or self-hosted capacity beats per-request
pricing. **That crossover is the trigger for item 2's AMD benchmark** — which is
why item 2 is blocked rather than merely deferred. These two items are the same
decision viewed from opposite ends.

## 7. Trial one vuln-detection AI tool in a non-prod pipeline

**Status: done.** Added `.github/workflows/codeql-trial.yml`.

### Why CodeQL, and why this was the right gap to fill

The repo had **no static application security testing at all**. `security.yml`
runs dependency review, a regex secret sweep and workflow YAML linting; none of
those read application logic. On a codebase whose control plane handles
checkout, Stripe webhooks and refunds, the bugs that matter are taint-flow bugs
— an untrusted request field reaching a query or a shell — and regex scanning is
structurally incapable of seeing them. CodeQL's semantic taint tracking targets
exactly that class.

### Trial posture — non-prod by construction, not by convention

- **`schedule` + `workflow_dispatch` only.** No `pull_request` trigger, so it
  cannot block a merge or be promoted to a required check by accident during the
  trial.
- **`continue-on-error` on init and analyze.** A scanner failure is trial noise,
  not a broken build. The trial is judged on findings, not on run colour.
- **`queries: security-extended`** — the wider net, including lower-confidence
  rules, because false-positive rate is one of the things being measured.
- **Least privilege:** top-level `contents: read`; the job widens only to
  `security-events: write` and `actions: read`.
- **SHA-pinned** to `e4fba868…` (v4.37.3), resolved from the upstream tag rather
  than assumed, per house convention.
- Scheduled Mondays 05:42 UTC, clear of the 04:17 multi-repo audit.

Verified: YAML parses, triggers are `['schedule', 'workflow_dispatch']`, matrix
covers `python` and `javascript-typescript`.

### Review criteria — 2026-08-24

Promote to a required PR check **only if all three hold**:

1. **Triage cost is sustainable** — the weekly alert volume can be worked
   through without the queue growing.
2. **Precision is high enough to trust** — a scanner people learn to dismiss is
   worse than no scanner, because it consumes attention and returns nothing.
3. **At least one finding is real** on the control plane's money-movement paths.
   If four weeks of `security-extended` across both languages surfaces nothing
   true, that is itself a result: either the code is clean or the queries are
   not aimed at our risk, and both change what we do next.

If promoted, it should gate `clearglass-commerce/**` first — the highest-value
paths — before repo-wide enforcement.
